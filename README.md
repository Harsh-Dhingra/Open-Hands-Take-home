# Tic-Tac-Toe with a real backend

**Run it.** `make install`, then `make run` and open http://localhost:8000: the page lets you play a friend (open the share link in a second tab) or the computer; the API docs are at `/docs`. `make test` runs the whole suite (526 tests, 100% coverage, with a hard 100% gate on the rules engine) and `make lint` runs ruff; `DB_PATH`, `PORT` and `SSE_KEEPALIVE_SECONDS` are the only settings (see `.env.example`). **Design.** The backend owns every rule and all state, and the browser only draws what the server returns. `app/engine.py` is pure code (no I/O): a game is an append-only log of moves, and the board, status, winner and winning line are always *derived* by replaying it. That log is what SQLite stores (`app/store.py`, behind a small repository interface), so the state can never disagree with its history, a restart cannot lose or change a game, and replay, concurrency and the computer player all fall out of the same model. Each move is one atomic read-modify-write, and a client can send the `expected_version` it last saw to be told (409 `stale_version`) instead of having a move applied to a board it was not looking at. FastAPI (`app/api.py`) is a thin layer that maps engine errors to stable codes (`cell_taken`, `not_your_turn`, `stale_version`, ...).

**Beyond the requirements.** I built the parts that show how the state model holds up, rather than polish: boards from 3×3 to 20×20 with any K in a row, games that survive a restart (tested with `kill -9`), two clients on one game with optimistic concurrency and live updates over Server-Sent Events, and a computer opponent with Easy, Medium and Hard (minimax) levels, where Hard is checked exhaustively against an independent oracle and cannot lose from either side. Each extra is a small step on the same move-log idea, which is why they stayed cheap to test. **AI tools.** I used Claude Code (Claude Sonnet 5.5) in the Claude desktop app, and worked plan first: it drafted `Plan.md` (scope, architecture, milestones, test strategy) and a short plan for each feature, which I approved or changed before any code, then built one milestone per branch in small commits. To review its output I leaned on mutation checks (breaking the code on purpose to see whether a test notices), exhaustive and oracle-based tests instead of hand-picked cases, and driving the real UI in the built-in browser; several real bugs were found that way and fixed, and they are described in the commit messages. API reference, the full test list and more detail are in [docs/DETAILS.md](docs/DETAILS.md).
